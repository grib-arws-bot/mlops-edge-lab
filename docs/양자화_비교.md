# GGUF 양자화 방식 비교 (2026-09-17 기준)

llama.cpp(GGUF) 양자화 방식을 고르면서 조사한 내용. "왜 Q4_K_M을 골랐는가"의 근거 문서.

## 먼저 — 세 가지 계열이 있다

llama.cpp의 양자화 방식은 크게 3세대로 나뉜다.

1. **Legacy(Q4_0, Q5_0, Q8_0 등)** — 32개 가중치 묶음마다 스케일 값 하나만 쓰는 단순한 방식. 계산이 빨라 초기에 많이 쓰였지만, 같은 비트수 기준으로 아래 K-quant보다 품질이 낮아 지금은 대부분 K-quant로 대체됨(Q8_0은 예외 — 8비트라 정밀도 손실이 거의 없어 여전히 "레퍼런스용"으로 씀)
2. **K-quants(Q2_K~Q6_K, 각각 _S/_M/_L 변형)** — 레이어마다 민감도가 다르다는 걸 이용해서, attention 출력이나 FFN 하향투영처럼 품질에 민감한 텐서는 더 높은 정밀도로, 덜 민감한 텐서는 더 낮은 정밀도로 섞어서 저장. **같은 파일 크기 기준으로 legacy보다 품질이 좋아서 사실상 기본 선택지.** 우리가 쓴 Q4_K_M이 이 계열
3. **I-quants(IQ1~IQ4)** — "중요도 행렬(imatrix)"이라는 별도 보정 파일을 먼저 만들어서, 그 보정치를 바탕으로 더 정교하게 압축. 2~3비트같이 극단적으로 압축해야 할 때 K-quant보다 품질이 낫지만, **imatrix를 먼저 만드는 추가 작업이 필요**해서 우리처럼 4비트대를 쓸 땐 이득이 크지 않음

## 비교표 (4B 모델 기준, f16 대비)

| 방식 | 계열 | 비트/가중치 | 크기(4B 기준 추정) | 품질 손실 | 비고 |
|---|---|---|---|---|---|
| F16/BF16(무양자화) | - | 16 | ~8.0GB | 없음(기준) | GPU 서버에서 학습·평가할 때만 씀, 엣지엔 너무 큼 |
| Q8_0 | Legacy | 8 | ~4.3GB | 거의 없음 | f16과 거의 구분 안 됨. "품질 기준선" 확인용으로나 씀 |
| Q6_K | K-quant | ~6.6 | ~3.3GB | 매우 적음 | 용량보다 품질이 중요할 때 |
| Q5_K_M | K-quant | ~5.5 | ~2.7GB | 적음 | **품질 우선 대안** — 코드·수치 계산처럼 정확도 민감한 태스크에 안전마진 필요할 때 |
| **Q4_K_M** | K-quant | ~4.8 | **~2.4GB(실측)** | 적당 | **채택.** "범용 기본값" — 크기 절반 이하로 줄이면서 품질 92~95% 유지가 일반적 평가 |
| Q4_K_S | K-quant | ~4.5 | ~2.2GB | Q4_K_M보다 조금 더 손실 | 용량이 조금 더 아쉬울 때 |
| Q3_K_M | K-quant | ~3.9 | ~1.9GB | 눈에 띔 | RAM이 정말 빠듯한 엣지 디바이스용 후보 |
| Q2_K | K-quant | ~2.6 | ~1.3GB | 크게 저하 | 이 크기(4B)에서는 비추천 — 모델 자체가 작아서 2비트까지 가면 품질 저하가 두드러짐 |
| IQ4_XS/IQ4_NL | I-quant | ~4.3 | ~2.2GB | Q4_K_M과 비슷하거나 약간 나음 | imatrix 보정 작업이 추가로 필요, 3비트 이하로 더 압축해야 할 때 진가를 발휘 |

## 결론 — Q4_K_M 채택 유지

- 실측 결과와 일치: 우리 4B 모델이 f16 7.5GB → Q4_K_M 2.3GB(약 3.2배 압축), CPU 생성 테스트에서 정확한 문장 생성 확인(`의사결정_로그.md` 24번)
- Q4_K_M을 "범용 기본값"으로 유지한다 — RAM이 더 빠듯한 실제 엣지 디바이스가 확인되면 Q3_K_M으로, 반대로 품질 이슈(과대판정·중국어 혼입 등, 20번 항목)가 양자화 때문인지 의심되면 Q5_K_M과 비교해서 원인을 좁힌다
- I-quant(imatrix)는 지금 단계에선 보류 — 4비트대에서는 이득이 크지 않고 보정 작업이 추가로 필요해서, 나중에 더 낮은 비트(2~3비트)로 내려야 할 이유가 생기면 그때 꺼낸다

## 실측 벤치마크 — CPU vs GPU (같은 Q4_K_M 파일, `llama-bench`)

같은 GGUF 파일 하나로 CPU 전용 빌드와 CUDA 빌드 둘 다에서 정상 동작 확인 — "GPU 있으면 가속, 없으면 CPU로도 동작"이 실제로 검증됨(디바이스별로 모델을 따로 만들 필요 없음).

| 백엔드 | 프롬프트 처리(pp128) | 생성(tg128) | 비고 |
|---|---|---|---|
| CPU (Xeon Silver 4510, 8스레드) | 202.97 t/s | 23.63 t/s | 엣지=GPU 없는 상황을 흉내낸 조건. **48코어 서버 기준이라 실제 엣지(노트북/미니PC)보다 낙관적** |
| GPU (RTX 4000 SFF Ada, 전체 레이어 오프로드) | 3793.27 t/s | 87.01 t/s | VRAM 2.32GiB만 사용 — 20GB 카드엔 여유 많음 |
| 배율 | 약 18.7배 | 약 3.7배 | GPU가 있으면 압도적으로 빠르지만, CPU만으로도 tg 23.6 t/s면 실시간 알림 생성엔 충분한 속도(문장 하나 생성에 1~2초대) |

빌드는 CMake 옵션만 다르게 두 개(`build/`=CPU 전용, `build-cuda/`=CUDA)로 분리해뒀다 — 같은 소스, 같은 GGUF 파일을 두 백엔드에서 그대로 비교할 수 있게.
