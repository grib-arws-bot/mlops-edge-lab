# 의사결정 로그

결정할 때마다 이 파일에 항목을 추가한다. 결정이 바뀌면 이전 항목을 지우지 말고 새 항목을 추가한 뒤 이전 항목에 "→ N번에서 변경됨"을 표기한다.

---

**1. (2026-09-17) 로컬 PC는 편집 전용, 실행은 전부 AI 서버에서** — "로컬 PC 미사용" 원칙은 학습/추론/서빙 같은 실제 작업을 로컬에서 돌리지 않는다는 뜻으로 해석. 코드 편집(VSCode)은 로컬에서 하되, 실행 환경은 AI 서버(`grib-ai-server`) 홈 디렉토리 하나로 통일.

**2. (2026-09-17) Python 환경 관리자 — `uv`** — 후보: `venv`(표준, 가장 단순) / `conda`(무겁고 이 서버엔 불필요) / `uv`(빠르고 lock 파일로 버전 고정). MLOps의 핵심 가치가 "실험 재현성"이라, lock 파일이 있는 `uv`를 선택. `~/mlops-edge-lab/.venv`에 파이썬 3.12 가상환경 생성.

**3. (2026-09-17) MLflow backend store — SQLite (`mlflow.db`)** — 파일 기반 저장소보다 조건 검색(실험 비교)에 유리하면서도 여전히 파일 하나라 백업이 쉬움. artifact store는 로컬 폴더(`~/mlops-edge-lab/mlflow/artifacts`)로 시작, 나중에 필요하면 교체.

**4. (2026-09-17) MLflow는 백그라운드에서 tmux 세션으로 실행** — SSH 접속이 끊겨도 서버 프로세스가 죽지 않게 하기 위함. 세션 이름 `mlflow`, `tmux attach -t mlflow`로 로그 확인 가능. (재부팅에는 안 살아남음 — 필요해지면 systemd user service로 승격 검토)

**5. (2026-09-17) MLflow UI는 SSH 터널로만 접근, 8081 포트는 쓰지 않음** — 서버에서 외부로 열린 유일한 포트(28081→8081)는 나중에 실제 sLLM 서빙 API가 써야 함. MLflow는 개인 전용 도구라 포트를 아낄 이유가 없고, 이미 인증된 SSH 접속을 재사용하는 터널이 더 간단하고 안전함(나 말고는 접근 불가). 접속 방법: `ssh -N -L 5000:127.0.0.1:5000 grib-ai-server` 실행 후 로컬 브라우저에서 `http://127.0.0.1:5000` 접속.

**6. (2026-09-17) 프로젝트 폴더 구조** — `~/mlops-edge-lab/{data/raw, data/processed, experiments, src, mlflow/artifacts, .venv}`. 원본 데이터·전처리 데이터·실험 코드·모델 산출물을 역할별로 분리.

**7. (2026-09-17) 문서 추출 — 형식별 폴백 사슬, BidRadar 설계 원칙 재사용** — BidRadar `extract.py`를 참고했으나, BidRadar 자체도 HWP 파서·LibreOffice 변환·OCR은 미구현 스텁이었음(prod 서버 사양 제약 때문). 이 프로젝트는 서버가 여유 있어 실제로 구현. "폴백 사슬"과 "조용한 빈 결과 금지"(실패 이유를 항상 기록) 원칙만 그대로 가져옴. `src/extract/core.py`.

**8. (2026-09-17) 레거시 포맷(HWP/DOC/XLS)은 LibreOffice headless → PDF 변환 후, 만들어둔 PDF 추출기를 재사용** — 포맷별 전용 파서를 따로 만들지 않기 위함. "텍스트 레이어 없음→OCR" 로직을 PDF 경로 한 곳에만 두면 포맷이 늘어나도 변환 단계만 추가하면 됨. PDF 라이브러리는 BidRadar의 `pypdf` 대신 `pymupdf`(fitz) 선택 — 텍스트 추출 품질이 낫고, OCR용 페이지→이미지 렌더링 기능이 같은 라이브러리에 있어 외부 도구(poppler) 불필요. AGPL 라이선스지만 사내 학습용이라 문제없음.

**9. (2026-09-17) OCR은 로컬 Tesseract(한국어 언어팩)** — 클라우드 OCR API 대신 완전 오프라인 동작을 선택. 엣지 배포 철학(네트워크 단절 환경 대응)과 일관성을 맞춤.

**10. (2026-09-17) 한글 zip 파일명 인코딩 버그 발견·수정** — Windows에서 만든 zip은 파일명이 CP949로 인코딩되는데 UTF-8 플래그가 꺼져 있어 리눅스 `zipfile`이 CP437로 잘못 해석함(`unzip -l`에서 깨진 이름 확인). `info.filename.encode('cp437').decode('cp949')`로 복원. `src/extract/walk.py`의 `fix_zip_filename`. 실제 데이터(738건, 성공률 99.9%)로 검증 완료 — 유일한 실패는 스캔 이미지 PDF(OCR 미설치 상태에서 실패 이유가 정확히 기록됨), HWP/DOC/XLS 레거시 경로는 아직 실제 샘플로 검증 못함.

**11. (2026-09-17) LibreOffice·Tesseract 설치 완료, HWP는 LibreOffice 대신 `pyhwp`로 전환** — 사용자가 BidRadar의 실제 문서 추출 현황표를 공유해줌: BidRadar는 HWP를 `pyhwp`(hwp5txt)만으로 LibreOffice 없이 완전 구현해뒀음이 확인됨. 더 가볍고 이미 검증된 경로라 우리도 pyhwp를 1차로, LibreOffice를 2차 안전망으로 변경(`_extract_hwp_pyhwp` 추가). DOC/XLS(구버전)는 BidRadar가 미구현으로 남긴 부분인데, 우리 서버는 LibreOffice를 이미 설치해뒀으니 그 경로를 유지 — BidRadar 대비 커버리지를 넓히는 지점.

**12. (2026-09-17) 확장자 오표기 대응 — 파일 시그니처로 재확인 후 재분기** — BidRadar 사례 참고: `.hwpx`인데 실제론 구버전 OLE 구조, `.hwp`인데 실제론 zip(HWPX) 구조로 저장된 실제 사례가 있음. 확장자만 믿지 않고 매직바이트(PK=zip, CFBF=OLE)로 실제 구조를 재확인해 올바른 경로로 재분기(`_effective_suffix`). TXT 지원도 추가(UTF-8→CP949→EUC-KR 순 디코딩, BidRadar와 동일 순서).

**13. (2026-09-17, 미해결로 남김) "738건 100% 성공"은 품질 검증이 아니다** — 사용자 지적: 지금 `ok=True` 판정 기준은 "빈 문자열이 아니고 글자수 임계값을 넘음"뿐이다. OCR이 오탈자투성이로 인식했거나, PDF에서 본문이 아니라 머리말/각주/목차만 뽑혔는데도 이 기준은 통과할 수 있다 — **추출 성공 ≠ 추출 정확**. 지금 당장 고치지 않고 기록만 해둔다. **향후 과제**: (a) 일부 문서를 사람이 원문과 대조해 샘플 검수, (b) 추출 결과에 대한 자동 품질 신호 추가 검토(예: 반복 문자열 비율, 사전 단어 매칭률, 페이지당 글자수 분포의 이상치 탐지), (c) 검수 결과를 골든셋으로 삼아 이후 추출 로직 회귀 테스트에 사용. `src/extract`를 건드리는 다음 작업 전에 반드시 재검토.

**14. (2026-09-17) GPU 4장이 맞음 — 이전 기록의 "3장"은 오기** — `nvidia-smi` 출력을 `head -20`으로 잘라서 본 탓에 3장으로 잘못 기록했었음(`nvidia-smi -L`로 재확인). `docs/전략.md`, `CLAUDE.md` 정정함.

**15. (2026-09-17) 로드맵 3번(파인튜닝) — 센서 데이터가 없어 임시 합성 데이터로 배관만 검증** — 실제 센서 스펙은 사용자가 별도로 정의해서 줄 예정(미착수). 지금은 "학습→MLflow 기록→평가"가 실제로 도는지만 확인하려고 `src/train/make_toy_dataset.py`로 임의의 센서 이벤트 템플릿 40건(학습 32/검증 8)을 만들어 사용 — **실제 데이터가 아니며, 센서 스펙이 오면 전량 교체 대상.** 결과(ROUGE-L 0.986)도 32건을 5 에폭 과적합시킨 수치라 품질 지표로 보면 안 됨, 배관 동작 증거로만 사용.

**16. (2026-09-17) 파인튜닝 스택 선택** — 베이스 모델 Qwen2.5-3B-Instruct(Apache-2.0, 한국어 준수, 엣지 목표 크기 1~3B와 일치). LoRA(r=16, alpha=32, target_modules=q/k/v/o_proj), bf16, 양자화 없음(3B가 20GB VRAM에 여유 있게 들어가 QLoRA는 더 큰 모델을 시도할 때로 미룸). `transformers`+`peft`+`trl`(SFTTrainer)+`accelerate`. 평가는 `rouge-score`(ROUGE-L)로 자동 채점 후 MLflow에 기록.

**17. (2026-09-17) RTX 4000 시리즈는 NCCL P2P/IB 비활성화 필요** — `accelerate`가 기본으로 GPU 간 고속 통신(P2P/IB)을 쓰려다 RTX 4000 시리즈(NVLink 없음)에서 `NotImplementedError`로 죽음. `NCCL_P2P_DISABLE=1 NCCL_IB_DISABLE=1` 환경변수로 해결. 이 서버에서 멀티/단일 GPU 학습 스크립트를 돌릴 때 항상 필요.

**18. (2026-09-17) 센서 스펙 반영 — 공기질/가스/조리흄** — 사용자가 실제 센서 카테고리·측정물질을 제공: 공기질(온도·습도·미세먼지·초미세먼지·CO2·TVOC), 가스(헬륨·질소·수소·아르곤), 조리흄(포름알데히드·아크롤레인·아세트알데하이드·VOCs·CO·NO2·벤조에이피렌·헤테로사이클릭아민·오일미스트). `make_toy_dataset.py`를 이 분류로 교체. **임계값 수치는 여전히 placeholder(공식 기준 아님)** — 실제 서비스 전 산업안전보건법 작업환경기준 등으로 교체 필요, 특히 벤조에이피렌·헤테로사이클릭아민·오일미스트는 저자가 정확한 공식 기준을 모른다고 명시.

**19. (2026-09-17) 베이스 모델 Qwen2.5-3B-Instruct → Qwen3-4B-Instruct-2507로 교체** — 상용 수준을 전제로 무료 오픈웨이트 모델을 비교(`docs/모델_비교.md`). Qwen3(Apache 2.0)를 채택 — 크기 선택지가 넓어 엣지~GPU서버를 한 계열로 커버 가능. EXAONE(한국어 최상이지만 NC 라이선스)과 Upstage Solar(한국어 우수하지만 최소 10.7B로 엣지에 안 맞음)는 제외. 같은 라이선스 계열 내 세대 교체라 코드 변경은 모델 이름 한 줄뿐, 재검증(장난감 데이터 재학습) 완료.

**20. (2026-09-17, 관찰만 기록·미해결) 평가 중 발견된 실패 유형 2가지** — 센서 스펙 반영 후 평가에서: ① "정상 범위"(임계값 이내)인데 모델이 "초과"로 잘못 생성한 사례(아르곤 4.6% vs 임계값 5.0%) — BidRadar의 "과대판정 방지" 원칙과 동일한 문제. ② 생성 중 중국어 단어가 섞여 나온 사례(수소 %LEL 케이스) — Qwen 계열이 중국어 데이터 비중이 커서 나타날 수 있는 현상. 둘 다 지금 당장 고치지 않고 기록만 함 — 실제 데이터로 재학습할 때 재현되는지 확인 필요.

**21. (2026-09-17) 실제 센서 "값"·정식 임계값 확보를 기다리지 않기로 결정** — 사용자 결정: 센서 카테고리·물질(18번)은 실제로 반영했지만, 정확한 계측값·공식 임계값 기준은 여전히 임의로 정해서 다음 단계로 진행한다. 로드맵 3번을 "배관 검증 완료, 실데이터 대기"가 아니라 **완료**로 처리. 정식 기준치 교체는 나중에 "실제 서비스화" 단계에서 처리할 별도 과제로 미뤄짐(18번 경고 유효).

**22. (2026-09-17) 로드맵 4번 — LoRA 병합 후 GGUF 변환·양자화** — llama.cpp가 베이스+어댑터를 실행 시점에 따로 얹는 방식을 안정적으로 지원하지 않아, `peft`의 `merge_and_unload()`로 먼저 통짜 모델을 만든 뒤 GGUF로 변환한다(`src/train/merge_lora.py`). GGUF 변환 의존성(`requirements-convert_hf_to_gguf.txt`)이 `torch==2.11.0`(CPU 빌드)을 강제로 설치하려 해서, 그대로 따르면 GPU 학습용으로 깔아둔 torch(cu121)가 깨질 뻔했음 — `gguf`·`sentencepiece`만 개별 설치해서 회피.

**23. (2026-09-17) llama.cpp는 CPU 전용으로 빌드** — 서버에 CUDA 드라이버는 있지만 `nvcc`(컴파일러)가 없어 GPU 빌드는 별도 작업(CUDA 툴킷 설치, sudo 필요) 필요. 지금 목적(엣지=GPU 없을 수도 있는 환경 검증)엔 CPU 빌드가 오히려 맞는 선택이라 그대로 진행. `cmake`도 sudo 없이 pip 휠로 설치해서 우회(`uv pip install cmake`).

**24. (2026-09-17) 양자화 Q4_K_M 결과 — 7.5GB → 2.3GB, CPU 19.1 tok/s** — `llama-quantize`로 f16(7672MiB) → Q4_K_M(2376MiB, 약 3.2배 압축). 서버 CPU(Xeon Silver 4510, 48코어) 8스레드로 실제 생성 테스트 결과 정확한 알림 문장 생성 확인, 속도는 프롬프트 142.9 tok/s · 생성 19.1 tok/s. **주의**: 이 속도는 48코어 서버 기준이라 실제 엣지 디바이스(노트북/미니PC급)보다 낙관적인 수치일 가능성이 큼 — 진짜 엣지 하드웨어 벤치마크는 7단계(실제 배포)에서 다시 재야 함.

**25. (2026-09-17) CUDA 툴킷 설치 + GPU 가속 빌드 추가, CPU/GPU 정식 벤치마크** — `sudo apt install nvidia-cuda-toolkit`(사용자 직접 실행, nvcc 12.0 확보) 후 `llama.cpp`를 `-DGGML_CUDA=ON`으로 `build-cuda/`에 별도 빌드(기존 CPU 전용 `build/`는 그대로 유지 — 같은 소스로 두 백엔드 비교 목적). `llama-bench`로 같은 Q4_K_M 파일 측정: CPU(8스레드) pp128=202.97 t/s·tg128=23.63 t/s, GPU(RTX 4000 Ada 전체 오프로드) pp128=3793.27 t/s·tg128=87.01 t/s(VRAM 2.32GiB만 사용) — 약 18.7배/3.7배 차이. 상세 근거는 `docs/양자화_비교.md`. **결론**: 하나의 GGUF 파일로 GPU 유무 두 조건 모두 실사용 가능한 속도가 나옴 — "런타임 하나로 이기종 대응" 설계 검증됨. pip 패키지(`nvidia-cuda-nvcc-cu12`)로 nvcc를 우회 설치하려 했으나 실제 nvcc 실행파일은 빠져있어(ptxas·nvvm만 포함) 실패 — 결국 정식 apt 설치로 진행.

**26. **32. (2026-09-17) 엣지 디바이스 자원 제약 에뮬레이션 방법 확립** — 실제 엣지 하드웨어가 없는 상태에서 "코어 수·메모리를 제한하면 어떻게 되는가"를 미리 검증하기 위한 방법. **할 수 있는 것과 못 하는 것을 먼저 구분**: cgroup으로 CPU 코어 수·메모리 상한은 실제로 제한 가능(하한선 추정용으로 유효), 반면 CPU 명령어셋(AVX-512 유무)·디스크 I/O 속도·발열 스로틀링 같은 실제 하드웨어 특성은 재현 불가 — "이 정도는 최소한 된다"는 하한선이지 정확한 예측이 아님.

**방법**: `systemd-run --user --scope -p CPUQuota=<N*100>% -p MemoryMax=<X>G -p MemorySwapMax=0 -- taskset -c <코어번호들> <명령>` (sudo 불필요, 유저 세션 cgroup으로 됨 — 확인 완료).

**실측**: 2코어(taskset 물리 코어 고정, `-t 2`)/32GB 상한 — tg128 **7.32 t/s**(8스레드 23.63 t/s 대비 약 3.2배 느림, 그래도 알림 문장 하나에 4~5초면 실용적).

**중요한 발견 — mmap+스왑 조합이 "조용한 정체"를 유발함**: 모델 크기(2.32GB)보다 작은 메모리 상한(2GB)을 걸었을 때, 스왑이 켜져 있으면 깔끔하게 실패하지 않고 **스와핑으로 무한정 멈춰버림**(30초 타임아웃까지 아무 출력도 없었음 — mmap 안 쓰는 `-lm none` 옵션으로도 동일). `MemorySwapMax=0`으로 스왑까지 차단하니 그제서야 즉시 OOM kill(exit 137, 20초 안에 종료)로 깔끔하게 실패함. **교훈**: 엣지 자원 제약 테스트에서 스왑을 반드시 꺼야 "이 메모리로 되는지 안 되는지"를 정확히 알 수 있다 — 안 그러면 "그냥 느린 것"과 "아예 안 들어가는 것"을 구분 못 하고 조용히 멈춰버린다(BidRadar의 "조용한 빈 결과 금지"와 같은 맥락의 함정).

**35. (2026-09-17) 파이프라인 페이지 개편 — 가로 흐름·역방향 루프 표시·MLflow 연동** — 사용자 요청 3가지 반영: ① 단계를 가로 배치 + 화살표로 연결(`.flow` flexbox), ② 각 단계에 정의·역할·모델/라이브러리 필드 추가, ③ "역방향 재학습 루프가 없냐"는 질문 — **정직하게 답함**: 설계상 2곳에 있음(3번 내부 "평가 미달 시 재학습", 6→2/3 "운영 피드백 루프") **but 둘 다 자동화는 안 되어 있음**. 화면에 점선 배지(`loop-badge`)와 하단 배너(`feedback-loop`)로 "설계됨·미자동화/개념적·코드 없음"을 명시해서 실제 구현 상태를 숨기지 않음.

**MLflow 연동 방식 — UI를 그대로 embed하지 않고 데이터만 가져옴**: MLflow UI 전체를 공개 페이지에 iframe으로 넣는 방법도 있었지만, MLflow UI는 실험 삭제 등 관리자 권한까지 있는 도구라 공개 노출은 부적절하다고 판단(의사결정_로그 5번의 "개인 도구는 SSH 터널로만" 원칙과 동일 연장선). 대신 `MlflowClient.search_runs()`로 최신 학습 run의 실측 지표(train_loss, eval_loss, 토큰정확도, ROUGE-L)만 API로 가져와 우리 카드에 표시하고, 더 자세히 보고 싶으면 SSH 터널 안내 문구를 남김. **"거짓 GPU 표시" 방지**: 서버 환경에 따라 GPU 재빌드가 실패할 수도 있으니, 기동 시 GPU 모델 로드에 실패하면 `EDGE_PROFILES`에서 `gpu: True` 항목을 통째로 삭제해버린다(`_load_gpu_llm_or_disable_gpu_profiles()`) — 드롭다운에 "GPU"라고 적힌 선택지가 실제로는 몰래 CPU로 도는 상황을 원천 차단.

**락 분리**: CPU 모델과 GPU 모델은 완전히 별개의 `Llama` 인스턴스(별도 KV 캐시)라 서로 동시에 써도 안전 — `_llm_lock`(CPU용)과 `_llm_gpu_lock`(GPU용)을 분리해서, 한쪽이 추론 중이어도 다른 쪽은 안 막히게 함(기존엔 락 하나로 CPU/GPU를 다 묶어서 불필요하게 직렬화할 뻔함).

**값 생성 시 물리적으로 불가능한 값 방지**: SEVERITY_RATIO(0.6/1.2/2.0배)를 곱하는 대신 나누는 걸로 방향을 바꾸면 "정상" 케이스에 18/0.6=30%처럼 대기 중 최대 산소농도(약 20.9%)를 초과하는 값이 나온다 — `sensors.VALUE_CEILING`으로 상한을 씌워서 방지. 검증: 정상→20.9%(재판정 시 ratio 0.86, 정상 유지)·주의→15.0%(ratio 1.20)·위험→9.0%(ratio 2.00, 위험) — 생성과 재판정이 서로 모순 없이 일관됨을 직접 스크립트로 확인.

**LLM 서술 방향 오해 방지**: `_event_prompt()`에 "낮을수록/높을수록 위험한 지표"를 명시하고, 정상 케이스의 규칙 생성 알림 문구도 "임계값 이내입니다" 대신 "안전 기준(X 이상)을 충족합니다"로 분기 — 안 그러면 산소 수치가 내려갔는데 LLM이 "초과했다"고 반대로 서술할 위험이 있었음.

**서버 관리자에게 요청한 것**: 위 3개 내부 포트(8082/8083/8084)에 대해 기존 28081→8081과 동일한 방식으로 외부 포트포워딩(28082/28083/28084) 추가.

(2026-09-19, 사고 기록) CI/CD 배포가 어제부터 조용히 실패하고 있었음 — 원인: SSH로 직접 만든 미추적 파일이 git pull을 막음** — 오늘 작업 마무리 중 우연히 `gh run list`로 확인하다가 발견. 어제(73번 작업 전) 스마트교육 실험을 SSH로 서버에서 직접 테스트하면서 `edu/experiment_rag_vs_no_rag.py`·PDF를 `scp`로 서버(`~/mlops-edge-lab`)에 먼저 올려서 돌려봤는데, 이후 로컬에서 같은 파일을 커밋·푸시하면서 **서버에는 같은 경로에 미추적(untracked) 파일이 이미 있는 상태**가 됐다. `scripts/deploy.sh`의 `git pull`은 미추적 파일을 덮어써야 하는 merge를 거부하고 에러로 죽는데, 이 실패가 `test-and-deploy` 잡의 `deploy` 스텝 실패로만 나타나고 아무 알림도 없어서(71번 Alertmanager-lite는 systemd 서비스 상태만 보지 CI 실패는 감시 대상이 아님) 하루 가까이 몰랐다. 오늘 커밋 푸시도 같은 이유로 또 실패하는 걸 보고서야 알아챔.

**해결**: 서버의 미추적 파일이 로컬에서 커밋한 내용과 실제로 동일한지 `git diff --ignore-all-space`로 먼저 확인(다른 내용이면 삭제가 위험하므로) → 확인 후 `git checkout --`(수정된 추적 파일 되돌리기)·`rm -rf`(미추적 파일 제거) → `git pull` 정상화(2커밋 fast-forward) → `deploy.sh` 재실행으로 정상 배포 확인 → 실패했던 GitHub Actions 런을 `gh run rerun`으로 재실행해 초록불 확인.

**재발 방지 관점의 교훈(아직 코드로 반영 안 함, 기록만)**: SSH로 서버에서 코드를 실험적으로 돌려볼 때, 그 파일이 나중에 git에 커밋될 경로라면 테스트 후 반드시 지우거나, 애초에 `~/mlops-edge-lab` 바깥의 임시 디렉터리에서 실행해야 한다는 걸 확인. CI 실패 자체를 감시하는 것도 71번 알림 체계의 사각지대라는 게 드러남 — 상용화 단계에서 알림 채널을 붙일 때(71번) systemd 상태뿐 아니라 "최근 CI 런 실패"도 감시 대상에 넣을지 고려할 만함.

**실서비스 영향은 제한적 — 이유**: `evaluate.py`는 LLM에게 원시 센서값·임계값만 주고 초과/정상 판정까지 스스로 하게 시키는 과제인데, 실제 운영 Agent(`src/agent/rules.py`, 30번 항목)는 판정을 규칙이 미리 내려서 LLM에게 "사실"로 알려주고 LLM은 문장 서술만 한다 — 그래서 이 평가가 재는 능력(판정+서술)과 실제 Agent가 LLM에게 요구하는 능력(서술만)이 정확히 일치하지 않는다. 다만 평가 스크립트 자체가 이 괴리를 인지하고 설계된 건 아니라서, "평가 과제가 실제 역할보다 어렵게 설계돼 있다"는 것도 가능성일 뿐 확정은 아니다.

**미해결로 남긴 것(사용자 결정 대기)**: THRESHOLD를 낮출지, 평가 프롬프트를 실제 Agent 프롬프트(판정 결과를 미리 알려주는 방식)에 맞게 다시 설계할지, 아니면 지금 그대로 두고 다음 정식 데이터로 재학습할 때 같이 재검토할지 — 아직 정하지 않음. `auto_retrain.py`를 재실행하지도 않았고(현재 Production 승격 상태는 그대로), 재학습 여부·게이트 값 조정은 사용자 확인 후 진행하기로 함.

**`train/make_edu_dataset.py` 신설 — 수집 데이터를 합성 QA로 재작성**: `make_toy_dataset.py`와 같은 "원문 그대로 학습 금지" 원칙. 차이는 원료가 비정형 산문이라 템플릿이 아니라 **LLM이 청크를 읽고 질문+답변을 생성**해야 한다는 것 — `allows_modification=True`인 수집 항목만(현재는 `nationalatlas_youth` 7건, KDI는 3유형이라 하드 제외) 청크(478개 후보)에서 60개 샘플링, JSON 파싱 실패 0건으로 전부 생성 성공.

**생성 데이터 수동 검수에서 발견한 문제**: 60건 중 최소 1건("제주도 지붕이 완만한 건 새가 살기 쉽게 하려고")이 원문에 없는 내용을 지어낸 것으로 보임 — 프롬프트에 "지어내지 말라"고 명시했음에도 발생. 안전 도메인의 결정론적 템플릿과 달리 LLM 기반 합성 생성은 이런 리스크를 구조적으로 안고 간다는 걸 확인. 지금 규모(n=60)는 배관 검증 목적이라 감수하고 진행, 규모를 키울 땐 원문 대조 검증 단계 추가가 필요.

**파인튜닝 실행·평가 — 결과: 문체는 배우지만 사실은 지어낸다**: `edu-social-lora` 어댑터 학습 성공(train_loss 0.94, GPU1에서 45초). 그런데 고친 채점(CharTokenizer, 75번)으로 평가하니 **평균 ROUGE-L 0.469**로 안전 도메인 게이트(0.90)에 크게 못 미침. 실제 생성 내용을 보면 원인이 명확: 질문에 답하는 **문체·형식은 48건만으로 금방 배우지만, 구체적 수치·연도·통계는 체계적으로 지어낸다** — 부산 인구(정답 3,349,016명→생성 3,433,000명), 서울/경남 소비지출(정답 200만원/52만원→생성 1,033만원/833만원, 완전히 다른 숫자), 서울시 구역 확장 연도(정답 1914→생성 1946) 등. 한 항목은 답변 끝에 구청명을 반복하는 생성 붕괴(degenerate loop)까지 나타남.

**결론 — 이 실험이 검증하려던 걸 정확히 확인함**: 안전 도메인에서 정립한 "RAG=사실, 파인튜닝=톤" 원칙(74·75번)이 교육 도메인에서도 그대로 적용된다는 걸 실측으로 재확인. 이 어댑터는 `toy-sensor-lora`처럼 **배관 검증용으로만 남기고 프로덕션에 쓰지 않음** — 교육 봇에서 사실 관련 질의는 반드시 RAG(수집 데이터 원문 인용)로 처리해야 하고, 파인튜닝은 안전 도메인처럼 "정해진 사실을 어떤 톤으로 서술하는가"에만 쓰는 것으로 범위를 좁힌다.

**부수적으로 짚은 것(사용자 지적)**: 산업안전 도메인의 "데이터 수집"은 원칙적으로 센서에서 상시 유입되는 실시간 데이터를 뜻해야 하는데, 지금은 `web/app.py`의 `_random_event()`가 만드는 시뮬레이션일 뿐 실제 수집 파이프라인이 아니다 — 오히려 이번에 만든 교육 도메인의 `src/collect/`가 이 프로젝트에서 처음으로 실제 외부 시스템에 상시 접속하는 진짜 수집 파이프라인이다. 실제 IoT 하드웨어가 붙으면, 그때 만들 실시간 수집 계층은 `_random_event()` 시뮬레이션이 아니라 `src/collect/`의 "상시 재실행 + 상태 추적" 패턴을 참고하는 게 나을 것으로 보임.

**81. (2026-09-19) 스마트교육 운영 콘솔(`/edu-admin`) 구현 — 수집 현황 + 학습 트리거 + "학생 체험"(RAG vs 파인튜닝 비교)**

**배경**: "운영자가 학습에 쓸 소스를 웹에서 선택"하는 설계(78번)를 실제로 만들면서, 사용자가 "학생이 실제로 쓴다는 관점에서 만들라"고 요청. 순수 파인튜닝 어댑터만 보여주면 오늘 확인한 hallucination(80번)을 그대로 노출하는 셈이라, RAG를 기본으로 하고 파인튜닝 단독을 비교용 토글로 두는 구조로 확정(사용자 선택: "둘 다").

**교육 도메인 RAG 인덱스 신설(`rag/build_edu_index.py`, `rag/query_edu.py`)**: 안전 도메인 `build_index.py`/`query.py`와 완전히 동일한 패턴(같은 임베딩 모델 `multilingual-e5-small`, 같은 청킹)이지만 별도 인덱스(`edu/processed/`)로 분리. **`edu/collected/`의 모든 수집 항목을 포함**(KDI처럼 `allows_modification=False`인 소스도) — RAG는 원문을 그대로 인용하는 것이라 "변경"이 아니므로 라이선스 문제가 없다는 79번 항목의 구분을 그대로 적용. 42개 수집 문서 → 2,679개 청크로 인덱스 구축.

**실측 — RAG와 파인튜닝 단독의 차이가 웹 UI에서 그대로 재현됨**: 같은 질문("부산광역시의 인구는?")에 RAG는 "1,405,037명(출처: 국가지도집... 인문환경)", 파인튜닝 단독은 "3,433,000명"(근거 없음, 80번에서 나온 것과 유사하게 지어낸 값)로 확연히 다르게 답함 — 다만 **RAG 답변의 숫자(1,405,037명)도 학습 데이터 생성 때 쓰인 참조값(3,349,016명)과 다르다**는 걸 확인했다. 같은 문서에 인구 관련 수치가 여러 개(연도·기준 상이) 있어서 검색 상위 청크가 매번 같지 않을 수 있다는 뜻 — RAG가 "환각은 없지만 항상 같은 근거를 찾는다는 보장도 없다"는 한계를 솔직히 남겨둔다. 그래도 최소한 **인용 가능한 출처가 붙는다**는 점에서 파인튜닝 단독보다 검증 가능성이 훨씬 높다.

**아키텍처 — 학습/추론 둘 다 별도 프로세스로 격리**: 웹 서비스가 이미 인프로세스 GPU 모델(llama_cpp, /simulate·/control-room용)을 띄워놓고 있어서, transformers 기반 파인튜닝·추론을 같은 프로세스에 얹으면 GPU 자원을 다툰다(finetune_lora.py에서 실제로 겪은 문제, 80번). 그래서:
- **학습 트리거**(`POST /api/edu-admin/train`) → `subprocess.Popen`으로 `train/run_edu_training_job.py`를 완전 별도 프로세스로 띄우고, `.health_state.json`과 같은 패턴의 상태 파일(`experiments/edu-social-lora/job_status.json`)을 웹이 3초마다 폴링(`GET /api/edu-admin/status`)해서 단계(합성 데이터 생성→파인튜닝→평가)를 보여줌.
- **파인튜닝 단독 비교 답변**(`train/ask_edu_adapter.py`) — 아직 GGUF로 변환 안 한 `edu-social-lora`를 transformers+PEFT로 그때그때 불러온다(느림, 수십 초). `asyncio`의 `run_in_executor`로 감싸서 다른 요청을 안 막게 함.
- **RAG 답변**은 반대로 이미 로드된 인프로세스 리소스(임베딩 모델·FAISS·llama_cpp)를 그대로 재사용해 빠르게 응답.

**라이선스 강제는 서버가 최종 책임**: 학습 소스 선택 체크박스는 `allows_modification=False`면 화면에서 비활성화하지만, `POST /api/edu-admin/train`이 선택된 소스를 다시 한번 서버에서 검증해서 거부한다 — 클라이언트 쪽 disabled 속성은 개발자도구로 얼마든지 우회 가능하므로, 실제 방어선은 서버 쪽에 둬야 한다는 원칙.

**실동작 검증**: 수집 현황 표(국가지도집 7건, KDI 35건) 렌더링 확인, RAG 질의응답 실호출 확인, 파인튜닝 단독 비교 응답 실호출 확인, KDI(변경금지) 소스로 학습 시도 시 서버가 정상 거부하는 것 확인, 웹에서 "학습 시작" 눌러 실제 서브프로세스가 뜨고 상태 파일이 갱신되는 것까지 확인.

**82. (2026-09-19) `/simulate` 복합 센서 시뮬레이션 — 여러 센서를 한 공간으로 간주해 LLM이 종합 의견 하나만 내도록 변경**

**배경**: 사용자가 `/simulate` 화면 스크린샷을 보여주며 지적 — 지금은 활성화한 센서마다 서로 다른 위치가 배정되고(`_default_location`이 슬롯 번호로 LOCS를 순환 배정) LLM도 센서마다 따로 알림 문장을 냈다. "모든 센서가 한 공간에 있다고 가정하고, LLM 결과는 복합 센서를 기반으로 의견을 줘야 한다"고 요청.

**설계 — 판정은 그대로 센서별, 종합되는 건 LLM 서술 하나뿐**: 물질마다 임계값·위험 기준이 다르므로 `rules.judge()` 판정과 장비 제어(`required_equipment_actions`)는 기존처럼 센서(이벤트)별로 독립 실행 — 여기를 뭉개면 판정 자체가 틀려진다. 종합되는 건 LLM이 마지막에 내놓는 설명 하나뿐이다. `agent/run.py`에 `run_agent_composite()` 신설 — 판정된 이벤트 전체를 하나의 프롬프트로 묶어 LLM에 한 번만 넘기고, "센서마다 따로 코멘트하지 말고 전체를 종합해 하나의 의견으로 정리하라"는 새 시스템 프롬프트(`_COMPOSITE_SYSTEM_PROMPT`)를 준다. 도구 호출 루프(가이드라인 검색)는 `run_agent`와 완전히 동일해서 `_run_llm_tool_loop()`로 공통화(중복 제거).

**위치 배정 변경**: `_default_location(idx)`(슬롯별 순환 배정) → `_default_location()`(요청 하나당 고정 위치 하나) + `_events_from_payload()`가 그 위치를 모든 이벤트에 동일하게 부여. control-room의 `_random_event()`는 원래부터 별개 함수라 영향 없음.

**엣지 에뮬레이션 경로까지 동일하게 처리**: `/simulate`는 프로파일에 따라 인프로세스(`_run_events_inprocess_composite`, 신설) 또는 cgroup 서브프로세스(`agent/run_cli.py`) 두 경로를 타는데, 후자는 `AGENT_COMPOSITE=1` 환경변수를 신설해서 서브프로세스 안에서 `run_agent_composite`를 타도록 분기(하위 호환 — 변수 없으면 기존 이벤트별 루프 그대로, control-room이 쓰는 `_run_events_emulated([event], ...)` 단일 이벤트 호출은 무영향). 실측: 인프로세스 17.66초, 4코어/8GB 에뮬레이션 40.25초 — 둘 다 3센서(정상/주의/위험) 입력에 대해 온도(위험) 중심으로 포름알데히드(주의)·산소(정상)까지 언급하는 종합 문장을 정상 생성.

**⚠️ 알려진 회귀 — 운영 피드백 루프(6→1/3번, 39번 항목) 프론트엔드 연결 끊김**: 기존 센서별 카드에 있던 👍/👎 피드백 버튼을 제거했다 — `train/incorporate_feedback.py`가 "이벤트 하나 + 알림 문장 하나"의 1:1 형태를 기대하는데, 종합 서술은 이벤트 여러 개에 문장 하나라 그 형태에 안 맞는다. 억지로 끼워 맞추면(예: 대표 이벤트 하나만 골라 종합 문장 전체를 그 이벤트의 정답으로 저장) 학습 데이터가 왜곡된다. **백엔드(`/api/feedback`, `incorporate_feedback.py`)는 그대로 남겨뒀다** — 다른 진입점이 생기면 여전히 동작하지만, 지금은 `/simulate`에서 피드백을 보낼 방법이 없다. 복합 피드백 형식(예: "이 종합 문장 중 어느 센서 서술이 틀렸는지" 같은 세분화된 평가)은 별도 설계가 필요한 후속 과제로 남겨둠 — 지금 당장 처리하지 않음.

**83. (2026-09-19) `/simulate` 엣지 에뮬레이션 성능 문제 2건 발견·수정 — "GPU 있어도 20초"라는 사용자 지적에서 출발**

**문제 1 — `ToolContext.load()`가 안 쓰일 때도 매번 7초 넘게 걸림**: 실측(모델 로드/컨텍스트 로드/추론 단계를 나눠 시간 측정)으로 병목을 찾았다 — GPU 모델 로드 0.96초, `run_agent_composite` 실제 추론 4.91초인데 `ToolContext.load()`(RAG 임베딩 모델+FAISS 인덱스 로드)만 7.48초였다. 이 로드는 LLM이 실제로 `search_guidelines`를 호출할 때만 필요한데, `agent/run_cli.py`는 매 요청마다 새 프로세스를 띄우면서 이걸 무조건 먼저 해뒀다 — 그런데 이번 테스트 케이스처럼 LLM이 도구 호출을 안 하면(판정·장비조치가 이미 다 결정돼 있어 안 찾아봐도 되는 경우가 흔함) 완전히 낭비되는 시간이었다. **해결**: `agent/tools.py`의 `ToolContext`를 지연 로딩으로 변경 — `load()`는 즉시 빈 컨텍스트만 만들고, `search_guidelines()`가 실제로 처음 호출될 때만 임베딩 모델·인덱스를 올린다(`_ensure_rag_loaded()`). 웹 서비스의 인프로세스 경로(`_state["ctx"]`)도 덩달아 서버 기동 시간이 빨라지는 부수 효과 있음. 수정 후 실측: `ctx_load 0.00초`, GPU 엣지 에뮬레이션 총 처리시간 20초 → 13.24초.

**문제 2(더 심각) — 타임아웃 시 systemd 스코프가 좀비로 남아 다음 요청까지 연쇄로 느려짐**: 위 수정을 검증하던 중 사용자가 "GPU 없는 프로파일에서 180초 타임아웃 났다"고 보고. 조사 결과 `_run_events_emulated()`가 `systemd-run --user --scope`로 만든 스코프 안에서 `taskset -c 0,1,2,3`으로 CPU 코어를 고정해 실행하는데, `subprocess.run(..., timeout=180)`이 타임아웃되면 파이썬은 자신이 직접 띄운 `systemd-run` "실행기" 프로세스만 죽이고, **그 실행기가 만든 스코프(실제 무거운 연산이 도는 곳)는 별개로 계속 살아있었다**. `ps aux`로 직접 확인: 타임아웃난 요청의 `agent.run_cli` 프로세스가 스코프째로 여전히 돌고 있었고(`systemctl --user list-units 'run-*'`로 스코프 유닛도 확인됨), 이게 같은 4개 코어(taskset 고정)를 다음 요청과 나눠 쓰면서 정상이면 20~40초 걸릴 일이 연쇄적으로 180초 타임아웃까지 번졌다. **해결**: `systemd-run --unit=<고유이름>`으로 스코프 이름을 직접 지정해두고, `subprocess.TimeoutExpired` 예외를 잡아서 `systemctl --user stop <스코프이름>`으로 명시적으로 정리하도록 수정. 발견 당시 남아있던 좀비 프로세스는 수동으로 정리(`ps`로 PID 확인 후 스코프가 이미 자연 종료된 것도 있었고, 진행 중이던 건 완료까지 기다림).

**교훈**: `subprocess.run(timeout=...)`은 "자신이 직접 spawn한 프로세스"만 책임진다 — 그 프로세스가 다시 systemd 스코프/서비스처럼 독립적인 생명주기를 가진 것을 만들면, 타임아웃 시 그 안쪽까지 자동으로 정리되지 않는다는 걸 실전에서 확인. 비슷한 패턴(서브프로세스가 또 다른 관리 단위를 만드는 경우)을 쓸 때는 항상 명시적 정리 경로를 같이 만들어야 함.

**84. (2026-09-19) `/simulate` 실행 기록 + 동시 실행 방지 — 구현 중 이벤트 루프 블로킹까지 발견·수정**

**요청**: 시뮬레이션을 여러 번 돌려도 기록이 남게 하고, 결과가 카드 형태로 쌓이게 하고, 하나 실행 중엔 다른 실행을 막아달라는 사용자 요청.

**구현**: `web/app.py`에 `_simulation_history`(메모리 리스트, 최대 20건, 최신순)와 `_simulation_in_progress` 플래그 신설. `/api/narrate`가 실행마다 `{id, created_at, edge_profile, edge_label, elapsed, composite, equipment}` 레코드를 만들어 히스토리 맨 앞에 쌓고, `GET /api/simulate/history`로 조회. 배포 재시작을 넘어 영구 보존할 필요는 없다고 판단해(대부분의 다른 런타임 상태와 동일 수준) 파일로 남기지 않음 — control-room 상태와 같은 성격. `simulate.html`은 결과 패널을 매번 덮어쓰던 것에서 카드를 누적(`prependRunCard`)하는 방식으로 변경, 페이지 로드 시 서버 히스토리를 불러와 새로고침해도 기록이 유지되게 함.

**동시 실행 방지 검증 중 더 큰 문제 발견 — `/api/narrate`가 이벤트 루프를 통째로 막고 있었음**: 두 요청을 동시에 쏴서 테스트했더니, 두 번째 요청이 409로 즉시 거절되는 게 아니라 **첫 번째가 끝날 때까지 그냥 먹통으로 대기**했다. 원인: `_run_events_emulated`(subprocess.run, 최대 180초 블로킹)와 `_run_events_inprocess_composite`(threading.Lock 획득 + LLM 호출)를 `await loop.run_in_executor(...)` 없이 async 핸들러 안에서 직접(동기로) 호출하고 있었다 — 이 경우 파이썬 asyncio는 그 호출이 끝날 때까지 **서버 전체**(control-room, edu-admin 등 다른 페이지 포함)가 어떤 요청도 처리 못 한다. control-room의 `_run_control_room_narrative`는 이미 `run_in_executor`로 감싸져 있어서 이 문제가 없었는데, `/simulate` 쪽엔 빠져 있었던 것. `_run_inprocess_composite_locked()`(락 획득까지 통째로 executor에 넘기는 래퍼) 신설 + `_run_events_emulated` 호출도 executor로 감싸서 해결. 수정 후 실측: 첫 요청이 진행 중이어도 `/control-room` 응답 0.01초, 두 번째 `/api/narrate` 요청은 즉시 409.

**동시성 테스트 도중 좀비가 또 발생 — 재시작 타이밍과 겹친 경우**: executor 수정을 배포하려고 `systemctl restart` 하는 타이밍에 직전 테스트(수정 전 버전)의 엣지 에뮬레이션이 아직 안 끝난 상태였는데, 스코프는 독립 생명주기라 재시작에도 안 죽고 계속 돌았다 — 그 상태에서 새 서버 인스턴스가 또 다른 에뮬레이션을 시작시켜서, 결과적으로 같은 4개 코어를 두 프로세스가 나눠 쓰는 좀비 상황이 재현됐다(`systemctl --user list-units 'mlops-edge-emu-*.scope'`로 실제 확인). **근본 대응**: 서버 기동(`lifespan`) 시점에 `mlops-edge-emu-*` 이름 패턴의 스코프를 전부 찾아 정지시키는 `_cleanup_orphaned_edge_scopes()` 추가 — 새 인스턴스는 이전 인스턴스가 뭘 하고 있었는지 전혀 모르므로, "내가 막 시작했는데 이 이름 패턴의 스코프가 이미 있다"는 건 전부 고아라고 판단해도 안전하다는 논리.

**89. (2026-09-19) RAG 품질 개선 1순위 — 하이브리드 검색(BM25+임베딩) 적용, 그 과정에서 프로덕션 SIGSEGV 발견·수정**

**수정**: `edu_admin_ask`의 "rag" 분기에서 `query_edu.answer()` 호출을 `with _llm_lock:`으로 감쌈(기존에 확립된 패턴을 그대로 재사용, 새 락 안 만듦). **검증**: 수정 배포 후 동일 질문을 2초 간격으로 6번 연속 요청(각 27~32초 소요 — 통합관제 틱과 겹칠 때마다 락 대기하느라 느려진 것, 의도된 동작) — 3분 넘게 겹쳤는데도 전부 200 OK, `journalctl`에 SEGV·루프 실패 0건으로 확인.

**수정**: ① 데이터 생성 모델을 F16 CPU 전용 → app.py 인프로세스 모델과 같은 조합(Q4_K_M + `n_gpu_layers=-1`)으로 교체. ② `generate()`/`build_and_save()`/`_load_modifiable_chunks()`에 `allow_restricted` 매개변수 추가, `run_edu_training_job.py`가 `--allow-restricted` CLI 플래그로 받아 `/api/edu-admin/train`이 동의 확인 후 이 플래그를 서브프로세스에 실제로 전달. ③ 진행률(`progress: "24/60"`) 상태 필드 추가 + 프론트 표시. ④ 학습 완료/실패 시점의 총 소요 시간을 서버가 `time.time()` 차이로 직접 계산해 `elapsed_seconds`로 남김 — 데이터셋이 작아 학습이 프론트 폴링 주기(3초)보다 빨리 끝나면 "진행 중" 상태를 한 번도 못 보고 바로 "완료"로 건너뛰어 클라이언트 타이머가 시작을 못 하는 경우에도, 이 값은 폴링 타이밍과 무관하게 항상 정확하다.

**검증(실측)**: 중단 후 재실행 — 25분+ → **4분 13초**로 완료. 생성된 데이터셋을 직접 열어 `kind` 분포 확인 결과 경제(KDI) 46건 / 지리 14건으로, 이번엔 KDI 콘텐츠가 실제로 학습 데이터에 포함된 것을 확인.

**93. (2026-09-19) AI 토론 기능 구현 — `/ai-debate`**

**배경**: `docs/전략.md`의 2차 후보였던 "AI 토론 배틀"(특정 주제에 참가자 의견에 따라 팀을 나누고 AI가 진행·심판)을 사용자 시나리오(학교/과목 선택→주제 입력/키워드 생성→학생 10여명 의견 에뮬레이션→그룹 분류→팀별 자료 제공→토론 후 재의견 수집·변화 분석)를 바탕으로 구현. 설계 논의 중 원안의 "임베딩 군집화로 그룹 분류"를 "LLM 분류(JSON) + 코드가 검증·그룹핑"으로 바꿨다 — 10명 안팎의 적은 표본에 군집화는 불안정하고, 이 프로젝트 전체의 "판정은 코드, LLM은 언어만" 원칙과도 어긋나서.

**API 3개**: `/api/edu-admin/debate/topic`(키워드→주제, 선택 단계), `/api/edu-admin/debate/start`(주제 확정→입장 카테고리 2~4개→학생 의견 생성(자유 텍스트, stance 태그 없이)→`_classify_stances()`로 분류→코드가 그룹핑→팀별 `query_edu.retrieve()` 재사용해 근거자료 확보), `/api/edu-admin/debate/conclude`(팀 자료를 반영한 토론 후 의견 재생성→**시작 때와 정확히 같은 `_classify_stances()`**로 재분류→코드가 전/후 stance를 비교해 유지/전환 집계).

**`_classify_stances()`의 방어적 설계**: LLM이 사전 정의된 categories 중 하나를 골라야 하는데, 자유 생성이라 카테고리에 없는 표현을 쓸 수 있다 — 파싱 후 categories에 실제로 있는 값인지 코드가 재검증하고, 없거나 개수가 안 맞으면 첫 카테고리로 안전 배정(토론이 멈추지 않게 하는 방어적 기본값이지 정확한 분류를 보장하진 않음, 정직하게 주석에 명시).

**전/후 비교를 왜 같은 분류기로 두 번 돌리나**: 처음에 "의견 생성과 동시에 LLM이 스스로 stance를 태그하게" 하는 방식도 검토했으나, 그러면 "전" stance는 자기 태깅, "후" stance는 별도 분류로 방법론이 달라져 비교가 일관되지 않는다 — 의견 생성(자유 텍스트)과 분류(사전 정의 카테고리 중 선택)를 항상 분리된 두 단계로 두고, 분류는 전/후 모두 `_classify_stances()` 하나만 쓰도록 통일.

**세션 상태는 서버에 안 두고 클라이언트가 들고 있음**: 로그인·사용자 세션이 없는 데모라, topic/categories/students/teams를 `/start` 응답으로 프론트에 전부 내려주고, `/conclude` 호출 시 그대로 다시 보내는 완전 무상태(stateless) 설계 — 서버 쪽에 세션 저장소를 새로 만들 필요가 없다.

**실측 검증**: "시장경제에서 정부의 역할은 얼마나 커야 할까요?" 주제로 학생 6명 생성 — 입장 4개(정부 간섭 최소화/산업 안정 보장/소비자 보호 강화/시장 유통 효율성 촉진)로 자연스럽게 분화, 팀마다 실제 경제교육 자료 3건씩 근거 확보(score 0.85~0.87). 토론 후 재수집에서 6명 중 3명 입장 전환, 답변에 "공공재", "비배제성/비경합성" 같은 팀 자료의 실제 개념이 반영된 것을 확인 — 근거자료가 실제로 의견에 영향을 주는 것으로 보임(엄밀한 통제실험은 아니고 정성적 관찰).

**AI튜터·산업안전과 마찬가지로 학습 중 잠금·GPU 경합 방지 적용**: 세 엔드포인트 모두 `_edu_job_status()`로 학습 중이면 409, `_llm_lock`으로 통합관제와 직렬화.

**94. (2026-09-20) BidRadar 연동 착수 — 첫 외부 연동 API `/v1/classify-doc` 구축**

**배경**: BidRadar(완전히 별개 프로젝트, ARWS 계열)가 Claude Docs로 공유한 "BidRadar sLLM 연동 요구사항" 문서를 검토 — 나라장터 입찰공고 분석에 전부 Anthropic API(Haiku/Sonnet)만 쓰다 보니 비용 때문에 일부 기능이 꺼져 있는데, 사내 sLLM으로 대체·보강 가능한지 타진. 검토 결과를 정리해 같은 문서에 회신 작성 → BidRadar가 A·B·C 세 유스케이스 전부 병행 진행을 요청, 사용자 확인 후 C(첨부문서 boilerplate 분류)부터 실제 구현 착수.

**"완전히 별개 프로젝트, 코드·인프라 안 섞는다"는 CLAUDE.md 원칙과의 관계**: 이건 BidRadar의 코드/저장소를 이 프로젝트에 가져오거나 그 반대로 하는 게 아니라, 이 프로젝트가 애초에 서빙 API 용도로 아껴뒀던 포트(28081→8081, 의사결정_로그 5번 "MLflow는 SSH 터널만 쓰고 8081은 나중에 실제 sLLM 서빙 API가 써야 한다")를 실제로 그 목적대로 쓰는 것 — 잘 정의된 API 경계로 별개 시스템을 연동하는 정상적인 서비스 통합이라고 판단.

**구현**: `POST /v1/classify-doc` — BidRadar 문서 4·5절의 스키마·공통 계약을 그대로 따름(`input_text`/`trace_id` 입력, `{is_boilerplate, reason}` 출력 + `model/tokens_in/tokens_out/latency_ms/trace_id`). BidRadar 문서 1절의 공통 원칙 3가지를 코드로 반영:
- **판정 금지** — is_boilerplate는 분류이지 "이 공고가 적합한가" 같은 최종 판정이 아님(BidRadar 원칙표 자체가 "추출·분류·정규화만"은 허용).
- **근거 필수** — reason에 원문 인용을 프롬프트로 요구.
- **조용한 실패 금지** — 인증 실패/빈 입력/JSON 파싱 실패 전부 `{"error": {"code", "message"}, "trace_id"}` 형태로 사유를 명시(빈 결과나 200 OK로 얼버무리지 않음).

**인증**: 내부망 토큰(`BIDRADAR_API_TOKEN`) — `ANTHROPIC_API_KEY`와 동일한 패턴으로 `systemctl --user set-environment`로 서버에 직접 등록, 저장소·채팅에 평문 노출 안 함. 토큰 값 자체는 BidRadar에 전달해야 해서 공유 문서(비공개)에는 기록.

**동시성**: 기존 `_state["llm"]`(산업안전 통합관제·AI튜터·AI토론과 공유하는 동일 CPU 모델 인스턴스)을 그대로 재사용하고 `_llm_lock`으로 직렬화 — 새 모델 인스턴스를 안 띄우는 대신, BidRadar에는 "진짜 동시 처리가 아니라 순서대로 대기"라고 사실대로 안내(8절).

**실측 검증**: 인증 없는 요청 401 확인, 제출서류 양식 안내문(공통서식) → `is_boilerplate: true` 정확 분류, 실제 사업 내용(IoT 센서 구축 사업 설명) → `is_boilerplate: false` 정확 분류, 둘 다 근거 인용이 원문에서 나옴.

**정직하게 기록한 한계**: 검증 중 한 건에서 reason 인용문 중간에 원문에 없는 토큰("tqdm")이 끼어든 사례 발견 — 소형 모델이 온도 0(결정적 디코딩)에서도 가끔 내는 돌발 토큰으로 보임. "근거 필수" 원칙상 인용이 정확해야 하는데 이 사례는 어긋남 — BidRadar의 20~30건 파일럿에서 빈도를 같이 확인하기로 함. 힘으로 고치지 않고(예: 사후 검증 로직 추가 등) 있는 그대로 보고한 것은, 아직 실제 빈도를 모르는 채로 대응책을 만드는 게 추측성 조치가 될 수 있다고 판단했기 때문 — 이 프로젝트가 "점수 마진 게이팅"(90번) 때 취한 태도와 같은 원칙.

**95. (2026-09-20) BidRadar 유스케이스 B·A 구현 — 사용자 지시로 우선순위 없이 병행 진행**

**배경**: BidRadar가 8절 계획에 동의하며 "합의된 C→B→A 순서대로" 진행을 요청했으나, 사용자는 "우선순위 없이 ABC 모두 진행"을 지시 — 서로 다른 두 지시가 충돌해 사용자에게 재확인 후, 사용자 지시(병행)를 따르기로 확정.

**B(시맨틱 필터) — `POST /v1/classify-topic`**: 공고 제목과 고객 관심주제를 의미적으로 매칭. 키워드 매칭이 놓치는 표현 변형을 잡는 게 목적이라, "자동화 설비 도입"이라는 제목이 키워드 "로봇"을 안 담고 있어도 "로봇/자동화" 주제와 매칭되는지가 핵심 검증 포인트 — 실측으로 confidence 0.98, 정확한 근거 문장과 함께 매칭 성공, 무관한 topic_id는 제외 확인. 완전 무관한 제목(도로 포장 공사)에 대해선 빈 배열 정상 반환. BidRadar와 합의한 대로 confidence는 서버에서 임의로 걸러내지 않고(예: <0.5 제외 같은 규칙 없음) 전부 그대로 반환 — 사람이 검토할 후보라는 성격을 서버 쪽에서도 훼손하지 않기 위함. LLM이 목록에 없는 topic_id를 지어내면 코드가 걸러낸다(AI토론의 `_classify_stances` 방어 패턴과 동일).

**A(나라장터 A2 대체) v1 — `POST /v1/extract-requirements`**: `rag/chunk.py`의 기존 청킹 함수를 재사용해 문서를 2,500자 단위로 나누고, 조각마다 요구사항을 추출해 합친다. **스코프를 의도적으로 축소**: BidRadar 원본 스키마(사업 항목별 세부·평가항목·예산조건·자격요건·제출정보 등 다수 중첩 필드)를 전부 구현하지 않고, requirements 배열 + summary 핵심 4필드(사업기간·예산·목적·담당자)만 먼저 구현 — 배열형 JSON이 항목 수에 비례해 깨지기 쉽다는 걸 92번에서 실측했는데, 필드가 훨씬 많은 중첩 스키마는 위험이 더 클 것으로 판단해 작은 스코프부터 안정성을 검증하기로 함. 근거 인용은 퀴즈 기능의 grounding 검증 함수(`_quiz_choice_grounded`, 88·89번)를 그대로 재사용 — 새 함수를 안 만들고 이미 검증된 걸 재사용.

**실측 검증**: 합성 공고 문서(사업개요+요건 2개 장, 약 900자, 1개 청크)로 테스트 — 요구사항 8건 전부 올바른 카테고리(성능/인증/실적/인력)와 수치로 추출, summary 4필드(사업기간 "계약체결일로부터 8개월", 예산 "3억 5천만원", 목적 원문 그대로 발췌, 담당자 부서/역할/전화/이메일)도 전부 정확. **레이턴시 49.5초** — max_tokens을 요구사항 추출에 800까지 열어뒀더니 실제로 850토큰을 생성했고, CPU 모델 실측 속도(23.6 tok/s, 의사결정_로그 22~25번)에 대입하면 대략 맞아떨어지는 수치 — 긴 문서·많은 요구사항일수록 비례해서 느려질 것으로 예상.

**tqdm 이상 토큰 재발견**: 이번 테스트의 8번째 요구사항(오탐율 3% 이하) cite 필드에서 또 "tqdm"이 끼어든 걸 발견 — 94번에서 처음 봤을 때는 "혹시 우연"이라고 여지를 뒀는데, 두 번째로 같은 현상(둘 다 숫자·퍼센트 표현 근처)이 나오면서 **우연이 아니라 이 모델의 실제 패턴일 가능성이 높아짐**. grounding 검증(토큰 70% 이상 일치)은 통과했다 — 인용문 전체가 아니라 토큰 단위 중복도로 판정해서, 한두 단어가 바뀌어도 대부분의 토큰이 원문과 겹치면 통과하는 구조이기 때문. "근거는 반드시 정확한 원문 인용"이라는 BidRadar 원칙 관점에선 이 정도 오차도 엄밀히는 위반 — 빈도·패턴(숫자 근처에서 자주 나오는지)을 더 확인해야 대응 방향(예: 숫자 포함 인용문은 더 엄격한 완전일치 검증)을 정할 수 있다고 보고, 아직 대응책은 적용하지 않고 관찰만 하는 중.

**추가 검증 — 멀티 청크(3,336자, 3개 청크) 재테스트로 확인**: 청크별 독립 호출 → 병합 자체는 정상 동작(7건 추출, summary는 첫 청크 기준으로 일관되게 유지). **다만 겹침 구간(overlap=200자)에 걸친 동일 요구사항이 두 청크 모두에서 각각 추출되어 중복으로 남는 것을 실제로 확인**("실적"·"인증" 항목이 2번씩) — v1은 중복 제거를 하지 않는다고 코드 주석에 미리 적어뒀던 게 실제로 관측됨. 문장 유사도 기반 중복 제거는 다음 이터레이션 과제로 남김(지금 억지로 넣으면 "비슷하지만 다른 두 요구사항"을 잘못 하나로 합칠 위험도 있어, 실제 파일럿에서 중복 발생 빈도를 먼저 보고 판단하는 쪽을 선택).

**96. (2026-09-20) A(요구사항 추출)를 GPU 서빙 + 동기→비동기(job 폴링)로 전환**

**배경**: BidRadar가 실측 레이턴시(청크당 ~50초, 중앙값 문서 15청크면 수 분)를 근거로 "상세페이지 열자마자 미리보기" UX와 안 맞는다고 문제 제기 — GPU 전환으로 줄일 여지가 있는지, 아니면 동기 대신 "백그라운드 생성+완료 알림" 구조로 바꿔야 하는지 질의. 사용자에게 확인한 결과 "둘 다 구현" 선택.

**GPU 전환**: `/v1/extract-requirements`가 그동안 통합관제·AI튜터·AI토론과 공유하는 CPU 전용 인스턴스(`_state["llm"]`)를 썼던 걸, 이미 존재하던 GPU 인스턴스(`_state["llm_gpu"]`, 통합관제 GPU 프로필·파인튜닝에만 쓰이던 것)로 전환. CPU vs GPU 실측 비교(4번, quantization_pipeline)에서 약 3.7배 차이가 난 걸 근거로 판단. 통합관제의 GPU 프로파일 추론과 동일하게 `_gpu_llm_busy` 플래그를 세워서(§27번 패턴 재사용) 실행 중엔 AI튜터 학습 시작을 막는다 — 물리 GPU를 학습(transformers 서브프로세스)과 공유하기 때문.

**동기→비동기 전환**: GPU로 바꿔도 "청크 수만큼 순차 호출"이라는 구조 자체는 없어지지 않아 GPU 단독으로는 "즉시 미리보기" 기대치를 못 맞춘다고 판단 — `POST /v1/extract-requirements`가 결과를 기다리지 않고 `job_id`를 즉시 반환(202)하도록 바꾸고, `GET /v1/extract-requirements/{job_id}`로 상태(`queued`/`running`/`done`/`error`)와 진행률(`chunks_processed`/`chunks_total`)을 폴링하는 구조로 전환. **이건 기존 계약을 깨는 변경**이라 BidRadar에 별도로 알려야 함. AI튜터 학습의 job_status 폴링(92번)과 같은 패턴을 재사용 — 새 패턴을 만들지 않음. job은 인메모리 딕셔너리(`_bidradar_jobs`, 최대 100개, 오래된 것부터 정리)로 유지, 서버 재시작 전까지만 보존(다른 인메모리 로그들과 동일한 한계).

**실측 검증**: 합성 요건 문서(1개 청크)로 async 흐름 전체(제출→job_id 수신→폴링→done) 실서버에서 확인. 5초 이내 완료(`latency_ms: 4457`), `model` 필드에 `-gpu` 접미사로 실제 GPU 경로를 탔음을 확인. `/bidradar` 통계 페이지에도 이 실제 호출이 정상 반영됨. cite 필드에서 95번에 기록한 것과 같은 유형의 토큰 오염("3초" → "eterminate")이 또 관측됨 — 세 번째 재현이라 빈도가 낮지 않다는 근거가 더 쌓였으나, 아직 대응책은 적용하지 않고 파일럿 데이터로 패턴을 더 확인하기로 한 기존 결정(95번) 유지.

**97. (2026-09-20) CD 파이프라인 실전 검증 중 배포 충돌 발견·수정 — scp 수동 배포와 git 배포의 혼용 문제**

**배경**: "CI/CD 작업하자"는 사용자 지시로 self-hosted 러너 상태를 확인했는데, 예상과 달리 이미 등록되어 있고 최근 배포들이 전부 성공한 상태였음(이전 세션 어딘가에서 등록된 걸로 보이며, "러너 미등록"이라던 기존 메모리 기록이 낡은 정보였음 — 메모리 갱신 필요). 이번 세션 동안 쌓인 4개 커밋을 push해서 실제로 CD가 도는지 검증하는 과정에서 배포가 실패하는 걸 발견.

**원인**: 이번 세션 내내(AI토론·BidRadar·오답노트 등) 기능을 배포할 때 매번 `scp`로 서버에 파일을 직접 복사하고 `systemctl --user restart`로 재시작하는 방식을 써왔다 — git 커밋 없이. 그 결과 서버의 git 워킹 트리에 "커밋되지 않은 로컬 변경"이 쌓여있었고, CD의 `git pull`이 이 변경사항과 충돌해 실패(`Your local changes... would be overwritten by merge`).

**확인**: 서버의 로컬 변경분과 새로 push한 커밋 내용을 파일별로 바이트 단위 diff — `app.py`는 CRLF/LF 줄바꿈 차이만 있었고(Windows에서 scp한 파일이라 CRLF, git 커밋은 LF로 정규화됨), 나머지 7개 파일은 완전히 동일했다. 즉 실제로 유실될 작업은 없었음을 먼저 확인한 뒤에 `git checkout --`로 서버의 로컬 변경을 지우고 `git pull` 진행 — 확인 없이 바로 덮어쓰지 않은 이유는 이 프로젝트 전체 원칙(작업 유실 방지)과 동일.

**교훈 및 앞으로의 방침**: CD가 실제로 동작을 확인한 지금부터는, 기능 배포를 scp가 아니라 **git push로 통일**한다 — scp+수동 재시작은 이제 문제를 예방하는 게 아니라 오히려 서버·git 상태를 어긋나게 만드는 원인이 되었기 때문. 라이브 디버깅 중 빠르게 한 파일만 찔러봐야 하는 예외적 상황이라면 scp를 쓰더라도, 안정화되는 대로 반드시 같은 내용을 커밋·push해서 서버와 git 이력을 다시 맞춰야 한다.
